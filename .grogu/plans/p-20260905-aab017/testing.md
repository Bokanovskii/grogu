# The `.plan` document graph — testing plan

## What you are auditing

A plan has become a typed graph with a browser editor, and Markdown has become
compiled output. Four things can be quietly wrong and everything else is
recoverable:

1. **A second source of truth appears.** Some path writes `<stage>.md`
   directly, or the browser keeps a model that can disagree with the graph, or
   a legacy `<id>/` survives beside `<id>.plan/`.
2. **The compiled artifact is not faithful.** Something in the graph does not
   render, renders in an unstable order, or renders differently on a second
   run — and the "semantic equivalence" claim is asserted rather than checked.
3. **The seal leaks.** A testing or evaluation node reaches an engineer through
   the graph, the HTTP API, a projection, an error message, an SSE event or an
   edge label.
4. **History is lost.** A crash, a concurrent write, a migration or a rejected
   patch destroys something instead of recording it.

Everything below exists to catch one of those four. Assume the implementation
looks correct; it will.

## Termination rule — read this before writing a single assertion

**The check list below is closed.** It has exactly 134 numbered checks. When all
134 pass with evidence, testing is complete. Do not generate additional checks by
enumerating clauses of the implementation plan's prose, and do not treat
"mutation survival" as the standard of proof.

This is not a stylistic preference. Plan `p-20260826-3f4d1a` in this repository
enumerated ~150 prose clauses, asked for a subTest per clause, and named
mutation survival as the completion criterion; it produced three defect rounds,
~45 new assertions, a gap list that never shrank, and an escalation — against a
correct implementation the whole time (harness friction #65, architect friction
#1). Any sentence can be weakened in a way no finite set of string assertions
catches.

Where a check asserts on prose or copy, it asserts on a **named literal string**
given in the check itself, and nowhere else.

If a genuine defect is outside all 134 checks, file it — the list bounds what you
must prove, not what you may report. But say explicitly in the defect that it is
out-of-list, so the architect can see whether the list was wrong.

The baseline before this plan, on `main`, is **706 tests, OK (skipped=6),
~92 s**. The integration branch `integration/p-20260904-6095a8` adds the review
suites. A drop in the passing count is itself a finding.

Fixtures you will need, and which you build yourself rather than reusing the
engineer's:

* **L** — a legacy plan directory with all four stages written, at least one
  Mermaid diagram in the design stage, at least six review threads including one

  existing `grogu plan`/`grogu review` CLI, not by hand-writing JSON.
* **P** — the same plan after `grogu plan doc migrate`.
* **B** — a synthetic graph of 400 nodes and 900 edges for the bounds and
  performance checks, generated by a script you write and keep under

Run the browser checks against a server you launch yourself, not against a
screenshot the engineer supplied.

## The checks

### A. One source of truth (1–10)

1. On a `.plan` plan, no code path other than the compiler writes `<stage>.md`
   or `<stage>.sealed`. Prove it by instrumenting `Path.write_text`/`os.replace`
   for the package directory during a full exercise (create, edit, comment,
   propose, accept, request-changes, finalize) and asserting every write to a
   stage artifact came from the compiler module.
2. Hand-edit `implementation.md` inside a `.plan` package. `plan doc verify`
   exits non-zero and names the file and both digests.
3. After (2), `plan doc compile` restores the file byte-for-byte to the
   compiled form and reports what differed.
4. After (2), `plan show --stage implementation` does **not** return the
   hand-edited bytes.
5. Create `<id>/` beside an existing `<id>.plan/`. Every one of `plan show`,
   `plan status`, `plan brief`, `plan gate`, `plan doc show`, `grogu review`
   refuses, and the message names **both** paths.
6. `grogu plan doc migrate` on a plan that already has `<id>.plan/` refuses and
   changes nothing on disk (compare a recursive digest before and after).
7. The browser holds no durable model: with the workspace open, write a node
   from the CLI, and assert the open page shows the change without a manual
   reload (SSE), and that a subsequent browser edit is based on the new
   revision.
8. Kill the server mid-session with an unsaved in-progress text edit. Nothing
   the user had *committed* is lost; the uncommitted textarea content is the
   only thing that may be gone, and reopening shows the last committed revision.
9. `git status --porcelain .grogu/plans/<id>.plan` after a full exercise lists
   only tracked artifacts: the stage `.md` files, `record.md`, `attachments/`.
   `graph/`, `log/`, `snapshots/`, `proposals/`, `projections/`, `legacy/`,
   `HEAD`, `manifest.json`, `review.json` and `*.sealed` are all ignored.
10. The `.grogu/plans/.gitignore` upgrade is **additive**: pre-seed the marker
    with an extra unrelated line, run any plan command, and assert the extra
    line survives and the new entries were appended.

### B. Compilation: determinism, fidelity, equivalence (11–28)

11. Compile the same revision twice in the same process: byte-identical.
12. Compile the same revision in two fresh processes with `PYTHONHASHSEED`
    differing: byte-identical.
13. Build the same logical graph by two different edit orders (insert A then B;
    insert B then A then reorder to match). Compiled output is byte-identical.
14. Every node in the graph appears in the reviewer projection of its stage.
    Assert by set comparison of ids, not by eyeball, on fixture **B**.
15. Every edge appears as a relationship line under its `from` node, or is
    accounted for in the sealed-edge count.
16. `parse(render(ir)) == ir` — Identity 2 — on fixture **B** and on **P**,
    field by field. Identities 1 and 3 are checks 117 and 119; this one alone
    does not establish faithfulness to the graph.
17. `render_json(ir)` and `render(ir)` carry the same node ids, kinds, titles,
    bodies, relationships, statuses and provenance. Compare programmatically.
18. Introduce a deliberate compiler bug in a scratch copy — drop the last
    relationship line — and confirm `plan doc compile --check` **fails** and
    names the differing field path. A check that cannot fail is not a check.
    `plan doc compile --check` must evaluate all three identities; assert it
    reports which one failed.
19. `task-9` sorts before `task-10` in every section.
20. Attribute maps render key-sorted; a node whose attrs were inserted in a
    different order compiles identically.
21. Output ends with exactly one newline, uses LF only, and has no trailing
    whitespace on any line.
22. The provenance block names the plan id, the revision, the projection, the
    compiler version, the graph digest and the projection digest, and the
    digests match what `plan doc show --json` reports.
23. Two different revisions produce different projection digests; the same
    revision recompiled produces the same digest (the cache is correct, not just
    warm).
24. A node body containing Markdown the subset renderer supports round-trips
    byte-identically through compile → parse.
25. A node body containing characters that stress canonicalisation — combining
    accents, a non-BMP emoji, a `~` and a `/` inside a key used in a JSON
    Pointer, CRLF, a lone surrogate rejected at input — either round-trips or is
    refused at write with a stated reason. Nothing is silently mangled.
26. A Mermaid diagram node compiles with its source intact and its parsed
    nodes/edges present as contained nodes.
27. `plan doc projection --since <rev>` lists exactly the directives added,
    changed and withdrawn since that revision — construct the expected set by
    replaying the log yourself.
28. Compiling fixture **B** (400 nodes, 900 edges) completes in **under
    500 ms** on this machine; report the measured figure.

### C. Bounded projections and elision (29–35)

29. With `--budget` large enough, nothing is elided and no `Elided` line
    appears.
30. With a budget that forces elision, the ladder is followed in the documented
    order: references/evidence bodies, then note bodies, then note nodes, then
    resolved threads, then decision rationale, then deep task bodies.
31. Every elided node is named by id and counted in the provenance block.
32. No `directive`, `constraint`, `invariant`, `criterion`, `goal`, `risk`,
    `question`, unresolved `thread` or relationship is ever elided, at any
    budget, including a budget of 1.
33. With a budget too small to hold the never-dropped set, the compiler exceeds
    the budget and says so, rather than dropping a directive.
34. Elision is deterministic: same graph, same budget, twice, byte-identical.
35. The bounded projection is still parseable — `parse(render(ir))` holds for an
    elided projection too.

### D. The seal and role isolation (36–48)

36. `graph/testing.sealed` and `graph/evaluation.sealed` are sealed on disk:
    the plaintext of a distinctive testing node title does not appear in the
    file bytes.
37. `grep -r` for that distinctive string across the whole package, excluding
    the sealed partition files, finds nothing — in particular not in `log/`,
    `snapshots/`, `projections/`, `proposals/` or `manifest.json`.
38. With `GROGU_ROLE=engineer`, `plan doc show`, `plan doc projection`,
    `plan doc impact` and `plan doc diff` never return a testing or evaluation
    node id, title or body.
39. With `GROGU_ROLE=engineer`, `GET /api/doc` response bytes contain no
    testing/evaluation node. Assert on the raw response body, not the parsed
    object.
40. An engineer-role patch whose op path targets a sealed partition is refused
    `403` **before** the op is parsed, and no revision is written.
41. An edge from an implementation node to a testing node is reported to an
    engineer as a count only. The count is right; no id, kind or title leaks.
42. An error message from a refused sealed access does not quote the node
    title, the path within the partition, or the sealed bytes.
43. SSE events delivered to an engineer session name only ids the engineer may
    see; a revision that touched only testing nodes delivers a bare
    `revision` event with no `changed[]` entries the engineer may not read.
44. `plan doc verify` as an engineer does not decode the sealed partitions
    (instrument `grogu_plans.unseal` and assert it is not called for them).
45. The workspace shows all four stage tabs; the sealed panel text is
    parameterised. On the Testing tab as an engineer it names **testing** and
    **engineer**, and on the Evaluation tab it names **evaluation** — the exact
    defect d6 regression from `p-20260904-6095a8`.
46. `POST /api/approve` with `GROGU_ROLE` set is refused, and the refusal comes
    from `PlanStore.approve`, not from a new check that could drift from it.
47. No command added by this plan accepts `--as-user`.
48. `plan finalize` on a `.plan` plan unseals exactly the stage artifacts it
    unseals today and does **not** unseal `graph/*.sealed`.

### E. Patches, revisions and atomicity (49–62)

49. The RFC 6902 Appendix A examples all behave as the RFC states, including
    the failing ones.
50. JSON Pointer escaping: a key containing `/` and a key containing `~` are
    addressable and round-trip.
51. A patch with a failing `test` op leaves the graph, `HEAD` and the log
    completely unchanged.
52. A patch whose 5th of 6 ops is invalid applies none of the first four.
53. A patch that would create a `depends_on` cycle is refused, and the message
    names the cycle.
54. A patch that would leave a dangling edge endpoint is refused.
55. A patch that is individually valid but produces a schema-invalid whole
    graph is refused — patch validity does not imply graph validity.
56. `base != HEAD` returns `409` with the current revision and the ops since the
    base, and writes nothing.
57. Two concurrent writers (two processes, same plan, same base) produce exactly
    one revision and one `409`. Run it 20 times; the count is 20/20.
58. A CLI write while the workspace is open produces one revision, an SSE
    event, and no lost update from either side.
59. Interrupt a write after the log file is written but before `HEAD` advances
    (inject the failure). On next load the store falls back to the newest
    complete revision, rewrites `HEAD`, and **reports** that it did.
60. Corrupt a partition file. The store rebuilds it from the newest snapshot
    plus the log, and the rebuilt bytes' digest matches the revision's
    `after_digest`.
61. Delete every snapshot. The store still rebuilds from `r0001`.
62. Ids are never reused: delete `task-7`, add three nodes, and assert no new
    node is `task-7` — including after a process restart.

97. None of the seven distinctive strings appears in any value returned by the

    structure, not by checking a rendered string.
98. None of them appears in `/api/control` or `/api/control/<agent>` raw

99. None appears in an exception message: force a parse failure, a size-cap

102. An **unregistered** session under `session-state/` is not read. Place one

103. Reading the dashboard creates no `activity.jsonl` record — the board

104. Bounds hold: a source larger than the initial tail, a line over the line

105. A truncated, rotated or replaced `events.jsonl` produces a gap marker and a

106. With source 2 absent entirely, the board renders, every agent from source 1

107. Orthogonality: kill the collector while an agent's lifecycle is
     `finished`. The row stays `finished` and `connection` becomes
     `disconnected`. Silence never rewrites a terminal state.
108. `quiet` versus `possibly_stuck`: an agent silent for 400 s with a healthy

109. `elapsed_basis` is `first_observed` and the figure is labelled a lower

110. Correlation: two agents whose `cwd` share a prefix, and two whose names

111. Every element carries `basis`; nothing rendered is unlabelled. An

112. Feedback: submitting binding feedback for an agent's role calls

## Evidence

### L. Compilation as core architecture (117–128)

Section B checks that compilation is deterministic and that render and parse
are inverses. This section checks the stronger claim the user's steering makes
binding: that the artifact is **equivalent to the source graph** and that
compiling is part of writing a revision rather than an export of one. Treat a
failure here as blocking regardless of how much else passes.

117. **Identity 1, completeness.** For every graph in the golden corpus and for
     every migrated real plan, and for each of the five role projections:
     `elements(projection) ∪ elided == elements(scope(graph, spec))`. Compute
     both sides yourself from `plan doc show --json` and compare as sets of
     ids. Report the three set differences, which must all be empty.
118. **Identity 1 catches an omission.** In a scratch copy, make `project` skip
     one edge kind. Identity 1 must fail and must name the missing edge ids.
     An identity that cannot fail is not an identity.
119. **Identity 3, graph equivalence.** `lift(parse(render(project(scope(g,s),s))))`
     compared structurally against `scope(g, s)` minus the elided set: node for
     node, edge for edge, attribute for attribute, body byte for byte. Run on
     the golden corpus and on `p-20260904-6095a8` after migration.
120. **Identity 3 catches a corruption that Identity 2 does not.** In a scratch
     copy, make `render` drop a directive's `audience` while `parse` restores a
     default for it. Identity 2 (`parse(render(ir)) == ir`) will still pass;
     Identity 3 must fail. Demonstrate both results — this is the check that
     justifies having three identities instead of one.
121. **Exhaustiveness fails closed.** Add a node kind and an edge kind to the
     closed tables without adding them to `scope`, `project` and `render`. The
     suite must fail, and the failure must name the kind. Confirm there is no
     default branch: grep the dispatch sites.
122. **Compilation gates the revision.** Force a compile failure — inject an
     exception in `render` — and submit a valid patch. Assert: no new file in
     `log/`, `HEAD` unchanged, partitions unchanged, compiled artifacts
     unchanged, and an error naming the identity, element and field. There must
     be no state in which the graph advanced and the artifact did not.
123. **Every accepted revision has a compiled artifact.** Drive 50 revisions
     through mixed CLI and browser writes. For each, assert a compiled artifact
     exists whose recorded source revision equals it and whose digest matches a
     fresh compile. 50/50.
124. **A proposal accepted produces a compiled artifact in the same
     transaction.** Accept a proposal; assert the compiled artifact advanced in
     the same revision, not on a later read.
125. **Golden corpus is a real gate.** Change one byte of compiler output — for
     example a separator — without regenerating the corpus. The golden test
     must fail. Then regenerate and confirm `git status --porcelain
     tests/fixtures/plandoc/golden` shows the reviewed diff.
126. **`COMPILER_VERSION` participates in the cache key.** Compile, bump the
     version, compile again: the second is a miss and produces a new artifact
     whose provenance names the new version. A cached artifact from an older
     version is never served.
127. **ETag and `--since` are correct, not merely present.**
     `GET /api/projection` returns a strong `ETag`; a repeat with
     `If-None-Match` returns `304` with no body; after any revision that
     changes that projection the `ETag` changes and a `200` is returned; after
     a revision that does *not* change it, the `ETag` is unchanged.
     `--since <rev>` returns exactly the directives added, changed and
     withdrawn and the nodes whose compiled digest moved — construct the
     expected set by replaying the log.
128. **Efficiency is measured, not assumed.** Warm-cache
     `plan doc projection --role engineer` on a migrated real plan: report the
     wall time and confirm it is a single file read (instrument `open`), with
     no graph load and no parse. Report the number.

     with a message naming the rule, and no revision is produced.
133. Kinds and `ext` follow opposite rules, deliberately. Demonstrate both in
     one test: an unknown *kind* raises and fails the build; an unknown *ext

134. SVG determinism: render the fixture flowchart twice from the pinned
     Mermaid settings (`deterministicIds: true`, `securityLevel: 'strict'`,
     `flowchart.htmlLabels: false`) and assert byte equality, and assert the
     manifest lists the SVG with a `renders` relationship to its Mermaid
     source.

## Evidence

* For each check: the command or test name, the observed result, and — for the
  measured ones (28, 76, 90, 95, 105, 108, 123, 128) — the number.
* For browser checks: a screenshot per mode per state, and the recorded request
  log for check 91.
* For the concurrency checks: the raw 20-run tally, not a summary.
* A check marked pass with no evidence is not a pass.

## Routing

* Wrong behaviour in Python or in the app → **engineer**, naming the workstream.
* The interface does not match the design spec → **designer**.
* A check that cannot be evaluated as written, or an acceptance criterion that
  is unverifiable → **plan**. That is a plan defect, not a pass.
* Your own harness wrong → keep it; fix it.
